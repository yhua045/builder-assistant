# Feature: React Native Embedding Service

## Goal

Provide a local embedding capability for the React Native application that uses the react-native-executorch library as the preferred default embedding provider for chunk text generated by the LangChain text splitter. This feature ensures the app can generate vector embeddings locally, persist those vectors in the SQLite vector database, and support local embedding-based search without depending on the project’s default remote embedding service.

This flow is limited to chunking, embedding, and embedding search within the mobile application. LLM inference remains outside this feature and is handled by the backend service through the API. The feature is intended to reduce dependence on external embedding infrastructure while keeping the system idempotent, observable, and safe under repeated processing or validation failure.

## System Flow

1. A document is processed into chunk text by the text-splitting workflow.
2. The system receives each chunk as the input to the embedding process.
3. The React Native embedding service attempts to generate a local embedding using react-native-executorch as the preferred default provider unless it is unavailable.
4. The system validates the chunk text and checks whether the same content has already been processed to avoid duplicate persisted embeddings.
5. The generated vector embedding is stored in the SQLite vector database alongside the chunk record or its related metadata.
6. Local embedding search can use the stored vectors to find relevant chunks, while LLM inference continues to be performed through the backend API.

## Acceptance Criteria

### AC1

**Given** a valid chunk generated by the text-splitting workflow,
**when** the embedding process is triggered,
**then** the system uses the React Native local embedding provider with react-native-executorch as the preferred default embedding path.

### AC2

**Given** the local embedding provider is available,
**when** a chunk is submitted for embedding,
**then** the system generates a vector embedding for that chunk without using the default non-local embedding service.

### AC3

**Given** the local embedding provider is not available or cannot initialize,
**when** an embedding request is received,
**then** the system retries automatically and, after the retry threshold is reached, fails the request and opens a circuit to stop further retries for that dependency until recovery.

### AC4

**Given** a chunk text is empty, whitespace-only, or otherwise invalid,
**when** the embedding request is processed,
**then** the request is rejected, the validation error is recorded, and no embedding vector is persisted for that chunk.

### AC5

**Given** the same chunk text is submitted more than once,
**when** the embedding process is retried or the same event is received again,
**then** the system treats the duplicate request as idempotent and skips creating a second persisted embedding record for the same content.

### AC6

**Given** a valid chunk is ready for storage,
**when** the embedding has been generated successfully,
**then** the vector embedding is persisted in the SQLite vector database and is available for local embedding-based search.

### AC7

**Given** a valid chunk has already been embedded and stored,
**when** a subsequent retry or duplicate request arrives with the same chunk text,
**then** the system does not create a duplicate vector record or duplicate embedding entry.

### AC8

**Given** an embedding generation or storage attempt fails due to a processing error,
**when** the failure occurs,
**then** the system records the relevant failure details and status in DocumentVersion and does not silently continue as though the embedding succeeded.

### AC9

**Given** the system is performing local chunking, embedding, and embedding search,
**when** a user or workflow requests search or retrieval based on embeddings,
**then** the system uses the local embedded vectors for matching and does not require the LLM inference path to perform the retrieval step.

### AC10

**Given** the application is using the local embedding flow,
**when** a document or chunk is processed,
**then** the LLM inference itself remains external to this feature and is executed through the backend API rather than locally in the mobile app.

## Error & Failure Handling

* If react-native-executorch cannot initialize or fails during embedding generation, the system must retry automatically and then fail the request with a circuit-break behavior after retries are exhausted.
* If the local provider fails, the system must not fall back to the default non-local embedding service for that request.
* If a chunk is invalid or fails validation, the system must reject it and record the validation result in DocumentVersion with the relevant status and error details.
* If an embedding write to the SQLite vector database fails, the system must treat the request as failed and prevent the application from reporting successful embedding storage.
* If a duplicate chunk is encountered, the system must skip reprocessing and preserve idempotency for repeated requests or automatic retries.

## Edge Cases

* Empty or whitespace-only chunk text.
* Duplicate chunk text across repeated requests or retries.
* A chunk that is valid in format but too large for local embedding generation.
* A transient runtime error while the local embedder is initializing or running.
* A local provider outage or unavailability at the time of request.
* A previously stored embedding record when the same chunk is processed again.
* A validation failure that must be tracked in DocumentVersion without creating a valid embedding record.

## Observability

* Log every embedding attempt with the chunk identifier and the selected provider status.
* Log validation failures and attach the failure reason to the relevant DocumentVersion record.
* Log retry attempts and the final failure outcome when the circuit breaker stops further retries.
* Log successful embedding persistence events, including the fact that the vector was written to the SQLite vector database.
* Track the local embedding flow separately from backend LLM inference so operational issues can be isolated to the correct layer.

## Out of Scope

* Performing LLM inference locally in the React Native app.
* Using the default remote embedding provider for this feature when react-native-executorch is available.
* Implementing retrieval ranking or response generation beyond local embedding search.
* Introducing unrelated document-processing workflows outside chunking, embedding, and local search.
